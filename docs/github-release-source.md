# GitHub Releases 源同步使用与配置指南

本文档面向模组作者与管理员，详细介绍如何在 SubmodHub 绑定与管理 GitHub Releases 作为模组内容源。

---

## 1. 核心设计与工作模式

- **外部源，权威在站内**：GitHub Releases 仅作为外部资产提供源。SubmodHub 会将 Release 资产下载到站内并完成 SHA-256 校验和静态安全扫描，写入不可变的站内归档与数据库。
- **发布归档严格不可变**：一旦版本在 SubmodHub 审核发布，该版本的二进制归档即永久锁定，即使 GitHub 上对应 Release 的资产被修改或删除，已发布内容不受任何影响。
- **版本号映射**：GitHub Release 的 `tag_name` 严格对应站内版本号（去除首尾空白，不擅自移除 `v` 前缀）。Release 的标题或正文作为初始候选版本发行说明。

### 1.1 版本发现：站内按需抓取 + 发版通知

站内**不再主动轮询** GitHub API。每个 `github_releases` 模组由作者在编辑窗口选择**怎么知道有新版本**，两种方式最终都汇入同一条下载 → 扫描 → 审核流水线。

| | 站内按需抓取 | 发版通知（推荐，默认选中） |
| --- | --- | --- |
| 作者需要额外维护文件 | 不需要 | **需要在仓库放一个 GitHub Action**，由站内生成，作者复制粘贴 |
| 站内何时回源 | 距上次检查超过 `GITHUB_SYNC_MAX_AGE` 时：有人打开该模组立即补抓，无人访问时由后台巡检兜底 | 同上，**外加**发 Release 时 Action 立刻通知一次 |
| 更新延迟 | 最多约 `GITHUB_SYNC_MAX_AGE`（默认 60 分钟） | 发版后几秒内开始检查 |
| GitHub API 配额消耗 | 每次回源 1 次条件请求（未变更时返回 304，不计配额） | 同上 |

选择建议：**想发完版就立刻上线就加那个 Action**；不加也照常工作，只是最多延迟约 60 分钟。

> 早期版本还有一个「仓库清单 `rezehub.yml`」模式（作者手写 YAML 列出所有版本）。它要求作者每次发版手动补记录，一旦忘记站内就永远看不到新版本，已被彻底移除；现在只有上面两种方式。

#### 发布即通知（推荐：复制一份生成好的工作流文件）

站内回源总要等到下一次窗口。要让 Release 一发布就检查，**不用自己写 YAML**：在作者工作台新建或编辑该 GitHub 托管模组，选择 **发版通知（推荐）**，点 **复制 GitHub Action 文件**，把复制到的内容粘贴到仓库的 `.github/workflows/rezehub-notify.yml` 并提交即可。

这份文件由服务器按当前配置生成，里面的站点地址、接口路径、以及**你自己填的 PC / Android 文件正则**一定是对的——这是手抄文档最容易出错的地方，所以不再手写示例。它做三件事：

- 只在 `release: types: [published]` 时运行（草稿不会触发）
- 把仓库自己的 `owner/repo`、release tag、**以及这组文件名正则** POST 给站内
- `continue-on-error: true`：通知失败不影响发布

正则随文件一起走，而不是只存在站内：作者改资产命名规则时改的就是自己仓库里那个文件，不会出现「站内改了正则、仓库里的 Action 还发旧的」这种两边不一致。

**源码包分配模式同样能生成这份文件。** 勾了「无匹配时使用 Release source code ZIP」、又没有文件名正则时，文件里没有正则可写，规则会带上 `shared_source_code`（分平台时是 `windows_source_code` / `android_source_code`）作为「这个仓库的包来自 Release 源码包」的记录，正文也会换成源码包说明，而不是让作者去找一条自己没填过的正则。通知接口接受这种不含正则的规则；下一次同步照旧按站内保存的兜底配置取包。

| 行为 | 说明 |
| --- | --- |
| 认证 | **不需要密钥**。请求里的 `owner/repo` 必须命中站内某个 `github_releases` 模组的绑定，否则返回 404 `not_found` 并丢弃；未绑定的仓库与写错仓库名表现完全一致，因此这个接口不能用来探测站内有哪些模组。 |
| 做了什么 | 只把该模组的 `github_last_sync_at` 清空（标记为过期），**不会**在请求里下载任何文件。请求里带的正则会先做 RE2 校验，不合法直接 400，避免把一个永远匹配不上的规则静默存下去。 |
| 之后的同步 | 照旧由现有链路完成：下一次有人打开该模组时被动回源，或由每分钟一次的后台巡检兜底。因此通知幂等、可重复发送。 |
| 一个仓库多个模组 | 绑定到同一 `owner/repo` 的模组会被同时标记为过期。 |
| 失败影响 | 退化成下面「6 小时版本自查」或「最多 60 分钟」的延迟，而不是漏同步。 |

#### 6 小时版本自查（不配置工作流也不会漏）

即使作者不装上面那份文件，站内也会每 6 小时自查一次。**读的是 Release tag，不需要作者维护任何文件**：

- 对每个 `github_releases` 模组，读取仓库**已发布 Release 中版本最高的 tag**
- 与站内**当前发布的最新版本**比较
- **只有 tag 高于站内版本时才触发一次同步**（同样只是标记过期），相同则什么都不做
- 跳过 draft 与 prerelease：两者都不会被导入，也不能当成新版本
- 取的是「列表里版本最高的 tag」，不是 `releases/latest`——后者按创建时间排序，补发旧版本或从分支发补丁会让它倒退
- `v1.0.0` 与 `1.0.0` 视为同一个版本，避免带 `v` 前缀的仓库每轮都误报
- 站内版本比仓库 tag 更新（例如仓库回退了 Release）也**不算**变化
- 探测失败（仓库还没有 Release、网络不通）**不算**发现新版本，但会把自查时钟向前推，避免坏仓库每分钟重试

每次自查消耗 1 次 GitHub REST 请求（6 小时 × 模组数，24 个模组约每小时 4 次，远低于配额）。

自查时钟 `github_version_checked_at` 与同步时钟 `github_last_sync_at` 相互独立：一次普通同步不会推迟下一次自查。

> 服务器主动拉取是**唯一**能覆盖所有仓库的方式：GitHub 不会在发 Release 时回调你的服务器，除非仓库显式配置 webhook 且站点暴露公网地址。工作流文件是秒级加速，6 小时自查是零配置兜底，两者可以同时存在。

## 2. 字段说明与配置步骤

模组作者在“新建模组草稿”或“编辑模组”弹窗中，可在“内容与版本来源”分段控件中选择 **GitHub Releases**：

| 字段名称 | 类型 | 必填 | 说明与示例 |
|---|---|---|---|
| `GitHub 组织/用户 (Owner)` | 字符串 | 是 | 仓库所属用户名或组织名，例如 `Monika-After-Story` 或 `octocat`。只允许字母、数字和连字符。 |
| `GitHub 仓库名 (Repo)` | 字符串 | 是 | 仓库名称，例如 `MonikaModDev` 或 `hello-world`。 |
| `版本发现方式` | 二选一 | 是 | **发版通知（推荐，默认选中）** 或 **站内按需抓取**，取舍见 [1.1](#11-版本发现站内按需抓取--发版通知)。 |
| `Release 资产文件名正则 (RE2)` | 正则表达式 | 条件必填* | 匹配 Release Assets 文件名的 Go RE2 正则。必须匹配 `.zip` 文件。例如 `^MyMod[-_]v?\d+\.\d+\.\d+.*\.zip$`。分平台模式下由各平台自己的正则接管；选「发版通知」时这条正则还会被写进生成的 GitHub Action 文件。**留空表示「不限文件名」，不是「跳过资产」**：此时按 tag 挑资产（`v1.2.0` 也按 `1.2.0` 匹配，且 tag 必须是完整的版本 token——`1.0.0` 不会命中 `mod-11.0.0.zip` 或 `mod-1.0.0.1.zip`），tag 也对不上但整个 Release 只有一个 ZIP 时直接取那一个，都不成立才轮到下面的源码包开关。**tag 同时命中两个以上 ZIP 时判为歧义**：同步记 `failed` 并列出候选文件名，不回退源码包、也不按字母序乱挑——此时请配一条正则消歧。 |
| `无匹配时使用 Release source code ZIP` | 布尔开关 | 条件必填* | 若 Release 未上传匹配的二进制 assets，是否允许自动使用 GitHub 自动生成的源码包 (`zipball_url`)。**两种版本发现方式都适用**：发版通知只负责把模组标记为过期，取哪个包仍由这里和上面的正则决定；因此源码包模式下生成的 Action 文件会带上对应的 `*_source_code` 标记，而不是一个空规则集。 |
| `资产分发方式` | 二选一 | 是 | **全平台共用一个文件（默认）** 或 **Windows / Android 分别匹配**（可只配置其中一个平台），取舍见 [2.1](#21-分平台分发)。 |
| `Windows / Android 资产正则` | 正则表达式 | 分平台时至少填一个平台 | 分平台模式下每个想支持的平台各填一条 RE2 正则（可各自单独开启源码包兜底），匹配同一次 Release 里的不同资产。**留空表示不发布该平台**；只填一个就只支持这一个平台。 |

*\* 注：必须至少配置资产文件名正则或开启源码包回退开关之一，否则配置校验不通过；分平台模式下由平台正则替代，至少要配置一个平台的规则（正则或该平台的源码包兜底），共用正则可留空。*

### 2.1 分平台分发

一个模组在同一时刻只有一种资产分发方式，不存在混用：

| 方式 | 存储字段 | 匹配行为 |
| --- | --- | --- |
| 全平台共用（默认） | `github_asset_regex` + `github_source_code` | 一次 Release 只取一个文件，所有平台下载同一份 |
| 分平台 | `github_platform_assets`（`windows`、`android` 至少一条） | 一次 Release 为每个已配置平台各取一个文件 |

- **默认规则：没分平台就是全平台兼容。** 未配置 `github_platform_assets` 的模组只产出一份归档，每个平台安装的都是同一份字节，下载时不带平台或带任意已知平台都等价（见 `docs/frontend-contract.md` 的下载语义表）。不要把「没有平台专用包」理解成「缺少某个平台」。
- 分平台模式**至少配置一个平台**，可以只支持 Windows 或只支持 Android：只填一个平台的规则就表示只支持该平台，另一个平台不会产出任何下载。留空（既不填正则也不勾选源码包兜底）即视为不发布该平台；已配置平台的规则必须可用，否则保存时被拒绝。
- **`supported_platforms` 由源配置派生，作者不能单独改它。** 保存分平台规则时（创建、编辑元数据、`PATCH /author/mods/{id}/source` 都算），服务端把 `supported_platforms` 置为规则里的平台，只配 Android 的模组因此不会出现在 Windows 的平台筛选里；切回共用文件（`github_platform_assets: []`）时，一个归档服务所有平台，服务端把它恢复为 `windows` + `android`，不会留下上一次分平台收窄的值。本地源不在此列，仍保留作者声明的平台集合。
- **原子性**：任一**已配置**平台在该 Release 里匹配不到 `.zip`（且未开启该平台的源码包兜底）时，这次 Release **整体跳过**并写入同步错误，错误信息里带缺失的资产名。永远不会出现“只发布了 Windows 版”的半成品版本。
- 切回共用文件时给 `github_platform_assets` 传空数组 `[]`，服务端据此清除分平台规则。
- 分平台版本在目录里的形状：版本级 `sha256`/`size_bytes` 为空，真实值在 `platform_assets: [{ platform, asset_name, size_bytes, sha256 }]`。每个平台的文件都由服务端落盘（源码包兜底的平台同样落盘并有真实哈希），`asset_name` 只记录来源文件名。
- 下载分平台版本必须显式指定平台：`GET /api/v1/versions/{id}/download?platform=windows|android`，省略时返回 400 `platform_required`——服务端不替客户端猜平台，避免把 Windows 包发给 Android 用户。反过来，**全平台共用文件的版本带 `platform` 是无害的**（等价于不带）：客户端可以每次都照自己的运行平台请求，历史版本不会因此失效；只有「不是平台的名字」（如 `linux`）才返回 404 `platform_not_found`。
- 本地上传源同样支持分平台：`POST /api/v1/author/versions/{id}/archive?platform=windows|android` 为每个平台分别上传归档，提交审核前必须每个平台都有文件**且都有各自的扫描报告**（否则 409 `archive_required` / `scan_required`）。每次上传只写该平台自己的报告键 `scan_<version>-<platform>`，重传 android 不会改写 windows 的报告；版本摘要的 `scan_report_id` 恒指向按 `windows`→`android` 顺序排在最前的那个平台，与最后一次上传的是哪个平台无关。

## 3. 正则表达式常见示例

SubmodHub 仅允许下载 `.zip` 格式的 Release 资产文件，非 `.zip` 文件即使匹配正则也会被自动忽略。

1. **精准版本前缀匹配**：
   ```regex
   ^MyMod[-_]v?\d+\.\d+\.\d+.*\.zip$
   ```
   匹配 `MyMod-v1.0.0.zip`、`MyMod_1.2.3-release.zip` 等。

2. **匹配任意包含 mod 名字的 zip**：
   ```regex
   (?i)MyAwesomeMod.*\.zip$
   ```
   忽略大小写匹配包含 `MyAwesomeMod` 且以 `.zip` 结尾的文件。

3. **排除特定平台的包**（例如只要 Windows 版）：
   ```regex
   ^MyMod-.*-windows\.zip$
   ```

   注意：若确实要「只要 Windows」，请直接用分平台模式，只给 Windows 填这条正则并把 Android 留空——这样 Android 就不会产出下载。共用模式下 Android 用户会拿到同一个 Windows 包，不能靠正则排掉。

4. **分平台模式下的典型一对正则**：
   ```regex
   Windows:  ^MyMod[-_]v?\d+\.\d+\.\d+[-_]windows\.zip$
   Android:  ^MyMod[-_]v?\d+\.\d+\.\d+[-_]android\.zip$
   ```

5. **多资产稳定排序规则**：
   若同一个 Release 存在多个资产文件命中正则，系统会按文件名进行稳定字母排序（Alphabetical Order），优先选择排序第一的资产，确保重复同步行为完全确定。分平台模式下每个平台各自套用这条规则。

## 4. 权限与入口保护机制

1. **创建候选版本拦截**：
   - 当模组配置为 `github_releases` 模式时，本站作者工作台隐藏“+ 创建候选版本”按钮。
   - 服务端接口 `POST /api/v1/author/mods/{id}/versions` 直接拦截并返回 HTTP 409 `github_source_managed`，防止版本源状态不一致。
2. **版本号不可篡改**：
   - GitHub 托管的版本在待审/上传状态下，允许作者通过 `PATCH /api/v1/author/versions/{id}/edit` 修订发行说明与依赖关联，但禁止修改 `Version` 标签。修改标签请求会被拒绝并返回 HTTP 409 `github_source_managed`。
3. **审核与发布流**：
   - 自动同步生成的版本默认进入 `ready_for_review`（待审核）状态，复用既有审核工作台，绝不绕过安全扫描与管理员审核。
   - 若系统配置了 `SUBMODHUB_AUTO_PUBLISH=true`，则同步通过扫描的版本自动标记为已发布。

## 5. 故障排查与运维

### 手动同步
在作者工作台进入 GitHub 托管模组时，可点击顶部操作栏的 **立即同步 Releases** 按钮：
- 接口地址：`POST /api/v1/author/mods/{id}/github-sync`
- 这是**强制同步**：会跳过 ETag 条件请求并重新对齐 `releases/latest`。
- 同步完成后，工作台将即时更新显示同步结果统计（新增版本数、跳过数、失败原因）。

### 回源时机与新鲜度
- 判定只有一个：距 `github_last_sync_at` 超过 `GITHUB_SYNC_MAX_AGE`（默认 `60m`，可在设置页修改）即为过期。
- 触发点一（被动）：`GET /api/v1/mods/{id}`（查看模组详情）、作者工作台列表加载（每次最多刷新 3 个过期模组）。
- 触发点二（巡检）：后台每分钟检查一次，把过期模组逐个回源，因此长时间无人访问的模组也会更新。
- 同一模组同时只允许一个同步在跑（单飞）；处于速率限制退避期时一律不回源。
- `GITHUB_SYNC_MAX_AGE=0` 表示关闭自动刷新，只有手动同步会回源。请求结果（版本数等）全部走异步刷新，不阻塞页面响应。

### 超限与不可导入的 Release 只探测一次
重复下载同一个永远无法导入的归档是纯浪费：它既不会生成版本记录，也会让下一个刷新窗口再跑一遍。同步流程对此只有一条判据——**拒绝结论属于那批字节，而不是那次尝试**。

- **下载前按 `asset.size` 预判**：Release 列表里的资产大小足以判断上限。声明大小超过 `SUBMODHUB_MAX_ARCHIVE_SIZE` 的资产直接判定为 `too_large`，不发出下载请求。旧流程要等数据流写到上限才报错，因此每个窗口都会白花这份带宽。
- **下载后才可能失败的，按 release 记录**：归档损坏、`ambiguous package roots`、清单声明（早期模式）的哈希不符等，重试同样的字节只会得到同样的结果。服务端把结论写入模组的 `github_release_failures`（含 `kind`、资产 ID/大小/名称、原因与时间），后续同步命中记录即跳过，不再下载。
- **记录按资产指纹失效**：记录与 Release ID、资产 ID、资产大小、资产名绑定。仓库替换资产会拿到新的资产 ID（通常大小也不同），旧记录自动不再命中。上限变化会让 `too_large` 结论失效。
- **强制同步是管理员的唯一重试入口**：`POST /api/v1/author/mods/{id}/github-sync` 忽略已记录结论重新下载；`too_large` 预判不受强制同步影响，因为上限没有变化时它必然失败。
- **重试门槛（按模组）**：记录是按资产指纹的，所以“同一份字节不重试”只挡住了同一次发布；打包结构错得离谱的仓库，没尝试过的历史版本会在第一轮被逐个下载（L&DL 的合集包 450 MB，一轮里被下过三份）。因此同一模组攒到 **2 条 `rejected`**（`githubRejectedAutoRetryLimit`）后自动同步暂停：此后只对**比所有已记录 Release 更新的版本**，或**同一个 Release 换过资产（同 tag 重新上传，指纹不匹配）**再花一次下载，从未尝试过的历史版本一律跳过。暂停**不按时间过期，只等作者更新**——新版本或换源会自动恢复，不需要人工清状态。跳过条目写明 `automatic sync paused after N rejected archives; waiting for a new release or a replaced asset`，同一句话也会写进模组的 `github_last_sync_error`（作者工作台直接显示这一行），所以暂停不会表现为“一个没有新版本的正常模组”；强制同步依旧重试全部。
- 被跳过的 Release 仍以条目形式出现在同步结果里：命中记录时记为失败，达到重试门槛时记为跳过并注明原因，不会静默消失；成功导入后对应记录会被清除。

### 分页与 ETag 缓存策略
- **分页拉取（Pagination）**：单次请求默认拉取每页最多 100 条（`per_page=100`）。若版本数量超过 100 条，系统会自动解析 GitHub RFC 5988 `Link` 分页头（跟随 `rel="next"`），支持拉取多页版本（设置安全保护上限 20 页 / 最多 2000 条 Releases），确保全部历史版本均能完整进入同步流程。
- **ETag 无条件保存**：首页响应返回的 `ETag` 在收到成功响应（HTTP 200）后无条件保存；即使仓库暂无 Release、列表为空或全部版本均已被过滤，也会完整保存 `newETag` 并在后续请求中持续发送 `If-None-Match`。未变更时返回 HTTP 304，完全不消耗内容配额。
- **304 不再额外请求 `releases/latest`**：列表返回 304 时直接认定无变更。此前每次同步都会再发一次无条件的 `releases/latest`，这是匿名配额（60 次/小时/IP）被打满的主因。手动同步仍会重新对齐 `latest` 标记。

### API 速率限制与自动退避（Rate Limit Backoff）
- **先在设置页配置令牌**：管理端「系统设置 → GitHub API 令牌」。未配置时所有请求共用匿名配额（60 次/小时/IP），托管模组一多就会撞限；配置后为 5000 次/小时。令牌保存即生效、无需重启，且只发给 API 主机，不会随资产下载外泄。配置了 `SUBMODHUB_DELIVERY_MASTER_KEY` 时令牌加密落盘，否则明文存储（设置页会明确标注当前是哪种）。
- **令牌只需要公开仓库的读能力**：站内只用两个只读端点——`GET /repos/{owner}/{repo}/releases` 与 `GET /repos/{owner}/{repo}/releases/latest`，没有任何写操作。Fine-grained token 选 `Public repositories (read-only)` 后 Permissions 可全部留空（GitHub 对公开仓库的只读能力是内置的）；Classic token **不勾任何 scope** 即可，空 scope 同样享有 5000 次/小时。仅当仓库是私有的，才需要 Fine-grained 选 `Only select repositories` 并加 `Contents: read`。不要给 `public_repo`——它包含公开仓库的写权限，对本站纯属多余。
- **自动解析重置时间**：当触发 GitHub API 速率限制（HTTP 403 / 429）时，系统自动解析响应头中的 `X-Ratelimit-Reset`（Unix 时间戳）或 `Retry-After`（秒数/标准时间格式）。若未提供具体头部，系统采用默认 15 分钟退避间隔。
- **保护性退避锁定**：退避期内，模组与后台全局同步器记录 `github_backoff_until` 截止时间。在截止时间到来前，系统定时轮询与手动同步将自动跳过外部网络请求，并在模组状态记录 `github_last_sync_error: github api rate limit backoff active until <UTC时间> (remaining: <剩余时间>)`，彻底防止短时间内连续空耗 IP 配额。更新代理或令牌会立即清空所有退避状态，因为配额桶已经换了。
- **自动恢复**：退避时间过后，下一次同步请求恢复正常执行，成功后自动清除退避状态。
- **设置页直接看用量**：令牌卡片会显示两个数字——「近 1 小时请求」是本进程近 60 分钟发出的 API 请求数（滚动窗口，含不收费的 304；重启或换令牌后归零），「官方配额已用 N / 5000」来自最近一次响应里的 `X-Ratelimit-Limit` / `X-Ratelimit-Remaining`（也包含共用同一把令牌的其他服务，且只在回源后更新）。两者口径不同，不要相互校正；代理摘掉配额响应头时只显示「等待下一次回源」。

### 切换回 Local 源与回滚演练
- 作者或管理员可在模组编辑窗口将来源切回 **本站上传 (local)**，或调用 `PATCH /api/v1/author/mods/{id}/source` 设置 `{"source_type":"local"}`。
- 切回 Local 模式后：
  - 立即恢复本站“+ 创建候选版本”入口与上传功能。
  - 此前已通过 GitHub 同步建立的既有版本及其归档完整保留，`source_type` 依然保留历史来源标记。
  - 删除草稿模组或下架模组绝不会删除历史已发布的不可变归档。

## 5. GitHub 全链路代理与服务端按需中转

SubmodHub 支持管理员在系统设置中配置全局 GitHub 代理。HTTP 代理可填写 `host:port`（例如 `100.106.239.85:7890`）或 `http://host:port`，HTTPS GitHub 请求通过 HTTP CONNECT 隧道传输；原有 `https://proxy.example/{url}` URL 重写模板仍受支持：

1. **代理覆盖范围**：
   - GitHub API 请求（仓库信息、Releases 列表、Link 分页）；
   - Release Assets 资产 ZIP 及源码 Source Code ZIP 同步下载；
   - 客户端模组下载时服务端的按需中转拉取（含 CDN 302 重定向）。

2. **代理服务要求**：
   - 代理服务必须同时支持 API 请求转发（保留 Accept/ETag/Link 头）与二进制文件流式下载。
   - 配置代理后，所有 GitHub 请求均严格走代理，代理失败时**不会静默回退至直连**，确保网络策略一致。

3. **发布一致性与下载交付**：
   - 发布哈希、大小及状态仍由主API决定；普通包当前latest后台复制到各启用Cloudreve，首次ready前独立读回验SHA-256。
   - 客户端先取下载描述，优先Cloudreve签名直链，其次授权GitHub节点，最终内置回落；各外部origin必须由API声明并受客户端校验，客户端最终哈希/大小失败不得安装。
   - GitHub转发和内置GitHub回落采用流式传输，不在每次客户端下载前落盘或重新扫描；已知大小不符在响应前拒绝，客户端必须在完整接收后校验发布SHA-256，不能把HTTP200当完整性证明。
   - 此部分替代原代理计划的强制同源下载约束。原主API GitHub出站代理仍服务同步与内置回落，独立节点可另配代理。

4. **历史与精灵包边界**：
   - 不自动搬运全部GitHub历史；站内已发布普通包可补Cloudreve，原始本地归档和旧镜像保留。
   - 精灵包整包、预览和按套选取继续由主服务器处理，不进入Cloudreve镜像调度。
   - 配置、独立认证探针及真实验收要求见[下载交付运维](download-delivery.md)。
